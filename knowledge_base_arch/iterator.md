# Итератор

## Суть паттерна

Итератор — это поведенческий паттерн проектирования, который даёт возможность последовательно обходить элементы составных объектов, не раскрывая их внутреннего представления.

## Проблема

Коллекции являются распространённой структурой данных в программировании. Они представляют набор объектов, организованных по определённым критериям. Хотя большинство коллекций выглядят как простые списки, существуют и более сложные варианты, построенные на деревьях, графах и других структурах данных.

Основная сложность заключается в том, что способы обхода могут меняться. Сегодня может быть достаточно обхода дерева в глубину, завтра потребуется обход в ширину, а позже — обход в случайном порядке. Добавление всех этих алгоритмов непосредственно в класс коллекции размывает её основную функцию (эффективное хранение данных) и приводит к загромождению кода. Некоторые алгоритмы могут быть слишком специализированы для конкретного приложения.

## Решение

Идея паттерна состоит в вынесении поведения обхода коллекции из самой коллекции в отдельный класс. Объект-итератор отслеживает состояние обхода, текущую позицию и количество оставшихся элементов. Это позволяет:

- Одновременно обходить одну коллекцию несколькими итераторами независимо друг от друга.
- Коллекция не знает о существовании этих итераторов.
- Добавлять новые способы обхода без изменения существующего кода коллекции.

## Структура

1. **Итератор** — описывает интерфейс для доступа и обхода элементов коллекции.

2. **Конкретный итератор** — реализует алгоритм обхода конкретной коллекции, отслеживает текущую позицию при обходе, позволяя разным итераторам обходить одну коллекцию независимо.

3. **Коллекция** — описывает интерфейс получения итератора. Коллекция может быть списком, базой данных, удалённым API или деревом (согласно паттерну Компоновщик), и может создавать подходящие для неё итераторы.

4. **Конкретная коллекция** — возвращает новый экземпляр определённого конкретного итератора, связав его с текущим объектом коллекции. Метод возвращает интерфейс итератора, позволяя клиенту не зависеть от конкретных классов.

5. **Клиент** — работает со всеми объектами через интерфейсы коллекции и итератора, не зависит от конкретных классов, может применять различные итераторы без изменения кода.

## Псевдокод

Пример использует паттерн для реализации обхода нестандартной коллекции, инкапсулирующей доступ к социальному графу Facebook. Коллекция предоставляет несколько итераторов (друзей, коллег), которые обходят профили по-разному. Все итераторы реализуют общий интерфейс, позволяя клиентам работать с профилями, абстрагируясь от деталей социальной сети. Итератор также избавляет от привязки к конкретным классам коллекций, облегчая добавление поддержки других сервисов (например, LinkedIn).

## Применимость

**Когда у вас есть сложная структура данных, и вы хотите скрыть от клиента детали её реализации.** Итератор предоставляет клиенту несколько простых методов перебора элементов, упрощая доступ и защищая данные от неосторожных или злоумышленных действий.

**Когда вам нужно иметь несколько вариантов обхода одной и той же структуры данных.** Нетривиальные алгоритмы обхода могут иметь объёмный код, который захламляет класс коллекции или бизнес-логику программы. Применив итератор, вы выделяете код обхода в собственный класс, упрощая поддержку остального кода.

**Когда вам хочется иметь единый интерфейс обхода различных структур данных.** Итератор позволяет вынести реализации различных вариантов обхода в подклассы, облегчая взаимозамену объектов итераторов в зависимости от структуры данных.

## Шаги реализации

1. Создайте общий интерфейс итераторов с обязательной операцией получения следующего элемента коллекции. Для удобства предусмотрите дополнительные методы: получение предыдущего элемента, текущей позиции, проверку окончания обхода и прочие.

2. Создайте интерфейс коллекции и опишите в нём метод получения итератора. Важно, чтобы сигнатура метода возвращала общий интерфейс итераторов, а не один из конкретных итераторов.

3. Создайте классы конкретных итераторов для тех коллекций, которые нужно обходить. Итератор должен быть привязан только к одному объекту коллекции — обычно эта связь устанавливается через конструктор.

4. Реализуйте методы получения итератора в конкретных классах коллекций. Они должны создавать новый итератор того класса, который способен работать с данным типом коллекции. Коллекция должна передавать ссылку на собственный объект в конструктор итератора.

5. В клиентском коде и в классах коллекций не должно остаться кода обхода элементов. Клиент должен получать новый итератор из объекта коллекции каждый раз, когда ему нужно перебрать её элементы.

## Преимущества и недостатки

**Преимущества:**
- Упрощает классы хранения данных.
- Позволяет реализовать различные способы обхода структуры данных.
- Позволяет одновременно перемещаться по структуре данных в разные стороны.

**Недостатки:**
- Не оправдан, если можно обойтись простым циклом.

## Отношения с другими паттернами

- Паттерн Компоновщик можно обходить, используя итератор.
- Фабричный метод используется вместе с итератором, чтобы подклассы коллекций создавали подходящие им итераторы.
- Снимок сохраняет текущее состояние обхода структуры данных для возможности вернуться к нему позже.
- Посетитель работает совместно с итератором: итератор обходит структуру, посетитель выполняет действия над каждым компонентом.
