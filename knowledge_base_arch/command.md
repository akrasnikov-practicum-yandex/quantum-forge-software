# Команда

## Суть паттерна

Команда — это поведенческий паттерн проектирования, который превращает запросы в объекты, позволяя передавать их как аргументы при вызове методов, ставить запросы в очередь, логировать их, а также поддерживать отмену операций.

## Проблема

Статья описывает ситуацию разработки текстового редактора с панелью управления. Создан класс красивых кнопок для использования повсеместно в приложении.

Все кнопки выглядят одинаково, но выполняют разные действия. Возникает вопрос размещения обработчиков кликов. Простое решение — создать подклассы для каждой кнопки и переопределить методы действия. Но этот подход имеет недостатки:

- Появляется очень много подклассов.
- Код UI начинает зависеть от классов бизнес-логики, которая часто меняется.
- Операции дублируются: одна функция (например, «сохранить») может вызываться из кнопки, контекстного меню и горячих клавиш, требуя повторения кода в нескольких местах.

## Решение

Хорошие программы структурируются слоями: UI и бизнес-логика отделены друг от друга. Обычно объект UI напрямую вызывает методы бизнес-логики.

Паттерн Команда предлагает иной подход: вместо прямых вызовов каждый вызов, отличающийся от других, оборачивается в собственный класс с единственным методом выполнения. Такие объекты называют командами.

К объекту интерфейса привязывается объект команды, который знает, кому и как отправить запросы. Когда UI готов передать запрос, он вызывает метод команды, а та позаботится обо всём остальном.

Классы команд объединяются под общим интерфейсом с единственным методом запуска. Отправители могут работать с различными командами, не привязываясь к их классам. Команды можно взаимозаменять на лету.

Параметры для вызова методов получателя сохраняются заранее в полях команды. Объекты, отправляющие запросы, не нуждаются в знании о получателе — вся информация инкапсулирована в команде.

В примере с текстовым редактором не требуется создавать множество подклассов кнопок. Достаточно одного класса с полем для хранения команды. Кнопки, контекстное меню и горячие клавиши привязываются к одинаковым объектам команд, устраняя дублирование.

## Структура

1. **Отправитель** — хранит ссылку на объект команды и обращается к нему при необходимости выполнить действие. Работает с командами только через общий интерфейс. Не знает конкретный тип команды, получает готовый объект от клиента.

2. **Команда** — описывает общий интерфейс для всех конкретных команд. Обычно содержит один метод для запуска команды.

3. **Конкретные команды** — реализуют различные запросы, следуя общему интерфейсу. Обычно передают вызов получателю (объекту бизнес-логики), а не выполняют работу сами. Параметры для обращения к получателю хранятся в полях. В большинстве случаев команды можно сделать неизменяемыми, передавая параметры через конструктор.

4. **Получатель** — содержит бизнес-логику программы. Могут быть практически любые объекты. Команды перенаправляют вызовы получателям. Иногда код получателя «сливают» в классы команд для упрощения.

5. **Клиент** — создаёт объекты конкретных команд, передавая необходимые параметры (включая ссылки на получателей). Связывает объекты отправителей с созданными командами.

## Псевдокод

Пример служит для ведения истории выполненных операций с поддержкой отмены.

Команды, изменяющие состояние редактора (вставка текста, вырезание), сохраняют копию состояния перед выполнением. Выполненные команды помещаются в стек истории для последующей отмены. Элементы интерфейса, история и другие компоненты работают через общий интерфейс команд, позволяя добавлять новые команды без изменения существующего кода.

## Применимость

**Когда нужно параметризовать объекты выполняемым действием.** Команда превращает операции в объекты, которые можно передавать, хранить и взаимозаменять. Например, при разработке библиотеки графического меню пользователи могут конфигурировать меню различными командами без изменения кода классов меню.

**Когда требуется ставить операции в очередь, выполнять по расписанию или передавать по сети.** Команды можно сериализовать в строку, сохранить в файл или базу данных, затем восстановить и выполнить. Аналогично их можно передавать по сети, логировать или выполнять на удалённом сервере.

**Когда нужна возможность отмены операций.** Главное для отмены — хранение истории. Паттерн Команда является одним из самых популярных способов реализации этого.

История команд представляет стек выполненных объектов команд. Каждая команда перед выполнением сохраняет текущее состояние объекта, с которым работает. После выполнения копия команды со сбережённым состоянием попадает в стек. При необходимости отмены программа извлекает последнюю команду из истории и восстанавливает сохранённое состояние.

Этот способ имеет две особенности: сложность точного сохранения состояния (помогает паттерн Снимок) и потребление значительной памяти копиями состояния. Альтернатива — команда выполняет обратное действие вместо восстановления, но это сложнее или невозможно в некоторых случаях.

## Шаги реализации

1. Создайте общий интерфейс команд и определите в нём метод запуска.

2. Один за другим создайте классы конкретных команд. В каждом должно быть поле для хранения ссылки на один или несколько объектов-получателей, которым команда перенаправляет основную работу. Кроме того, команда должна иметь поля для хранения параметров, необходимых при вызове методов получателя. Значения всех этих полей команда получает через конструктор. Реализуйте основной метод команды, вызывая в нём методы получателя.

3. Добавьте в классы отправителей поля для хранения команд. Обычно отправители принимают готовые объекты команд извне — через конструктор или через сеттер поля команды.

4. Измените основной код отправителей так, чтобы они делегировали выполнение действия команде.

5. Порядок инициализации объектов должен быть следующим: создаются объекты получателей; создаются объекты команд, связанные с получателями; создаются объекты отправителей, связанные с командами.

## Преимущества и недостатки

**Преимущества:**
- Убирает прямую зависимость между объектами, вызывающими операции, и объектами, которые их непосредственно выполняют.
- Позволяет реализовать простую отмену и повтор операций.
- Позволяет реализовать отложенный запуск операций.
- Позволяет собирать сложные команды из простых.
- Реализует принцип открытости/закрытости.

**Недостатки:**
- Усложняет код программы из-за введения множества дополнительных классов.

## Отношения с другими паттернами

Цепочка обязанностей, Команда, Посредник и Наблюдатель показывают различные способы работы отправителей запросов с получателями:
- Цепочка обязанностей передаёт запрос последовательно через цепочку потенциальных получателей.
- Команда устанавливает косвенную одностороннюю связь от отправителей к получателям.
- Посредник убирает прямую связь, заставляя общаться через себя.
- Наблюдатель передаёт запрос одновременно всем заинтересованным получателям с динамической подпиской.

**С Цепочкой обязанностей**: Обработчики могут быть реализованы как Команды. Множество операций выполняется над одним контекстом (запросом). Альтернативно — сам запрос является Командой, посланной по цепочке, и одна операция выполняется над множеством контекстов.

**С Снимком**: Используются вместе для реализации отмены. Команды отвечают за выполнение действия, Снимки хранят резервную копию состояния перед запуском команды.

**С Стратегией**: Похожи по духу, но отличаются масштабом. Команду используют для превращения разнородных действий в объекты, параметры становятся полями; объект логируется, хранится в истории, передаётся во внешние сервисы. Стратегия описывает разные способы произвести одно действие, позволяя взаимозаменять способы в объекте контекста.

**С Прототипом**: Помогает при копировании Команды перед вставкой в историю.

**С Посетителем**: Рассматривается как расширенный аналог Команды, способный работать с несколькими видами получателей.
