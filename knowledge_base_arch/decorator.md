# Декоратор

## Суть паттерна

Декоратор — это структурный паттерн проектирования, который позволяет динамически добавлять объектам новую функциональность, оборачивая их в полезные «обёртки».

## Проблема

В сценарии разрабатывается библиотека оповещений с базовым классом `Notifier`, отправляющим сообщения по email. При добавлении новых каналов (SMS, Facebook, Slack) встала необходимость поддерживать комбинации этих способов доставки.

Попытка решить это через наследование привела к «комбинаторному взрыву» подклассов: каждая комбинация требует отдельный класс. После добавления десяти классов стало очевидно, что этот подход неработоспособен.

## Решение

Вместо наследования используется композиция. Один объект содержит ссылку на другой и делегирует ему работу, добавляя своё поведение.

Декоратор имеет альтернативное название — обёртка. Оно более точно описывает суть паттерна: вы помещаете целевой объект в другой объект-обёртку, который запускает базовое поведение объекта, а затем добавляет к результату что-то своё.

Все объекты (базовые и декораторы) реализуют общий интерфейс, позволяя использовать несколько обёрток одновременно для получения объединённого поведения.

## Структура

1. **Компонент** — определяет общий интерфейс для обёрток и оборачиваемых объектов.

2. **Конкретный компонент** — определяет класс оборачиваемых объектов, содержит базовое поведение, которое затем изменяют декораторы.

3. **Базовый декоратор** — хранит ссылку на вложенный объект-компонент (может быть как конкретный компонент, так и другой декоратор). Делегирует все операции вложенному объекту. Дополнительное поведение реализуется в конкретных декораторах.

4. **Конкретные декораторы** — различные вариации декораторов, содержащие добавочное поведение. Выполняют свои действия до или после вызова поведения обёрнутого объекта.

5. **Клиент** — оборачивает простые компоненты и декораторы в другие декораторы, работая со всеми объектами через общий интерфейс.

## Псевдокод

Пример защищает финансовые данные дополнительными уровнями безопасности (шифрованием и сжатием) прозрачно для использующего код. Приложение оборачивает класс данных в шифрующую и сжимающую обёртки, которые при чтении выдают оригинальные данные, а при записи — зашифрованные и сжатые.

Декораторы и базовый класс имеют одинаковый интерфейс, поэтому клиентский код работает одинаково с «чистыми» объектами и обёрнутыми.

## Применимость

**Добавление обязанностей на лету.** Когда вам нужно добавлять обязанности объектам на лету, незаметно для кода, который их использует. Объекты помещают в обёртки, имеющие дополнительные поведения. Обёртки и сами объекты имеют одинаковый интерфейс, поэтому клиентам без разницы, с чем работать — с обычным объектом данных или с обёрнутым.

**Невозможность расширения наследованием.** Когда нельзя расширить обязанности объекта с помощью наследования. Во многих языках программирования есть ключевое слово `final`, которое может заблокировать наследование класса. Расширить такие классы можно только с помощью Декоратора.

## Шаги реализации

1. Убедитесь, что есть один основной компонент и несколько опциональных дополнений или надстроек.

2. Создайте интерфейс компонента, описывающий общие методы для основного компонента и его дополнений.

3. Создайте класс конкретного компонента с основной бизнес-логикой.

4. Создайте базовый класс декораторов с полем для хранения ссылки на вложенный объект-компонент. Все методы базового декоратора должны делегировать действие вложенному объекту.

5. И конкретный компонент, и базовый декоратор должны следовать одному и тому же интерфейсу.

6. Создайте классы конкретных декораторов, наследуя от базового. Каждый должен выполнять добавочную функцию, затем вызывать эту же операцию обёрнутого объекта.

7. Клиент берёт на себя ответственность за конфигурацию и порядок обёртывания объектов.

## Преимущества и недостатки

**Преимущества:**
- Большая гибкость, чем у наследования.
- Позволяет добавлять обязанности на лету.
- Можно добавлять несколько новых обязанностей сразу.
- Позволяет иметь несколько мелких объектов вместо одного объекта на все случаи жизни.

**Недостатки:**
- Трудно конфигурировать многократно обёрнутые объекты.
- Обилие крошечных классов.

## Отношения с другими паттернами

- **Адаптер vs Декоратор**: Адаптер предоставляет совершенно другой интерфейс для доступа к существующему объекту. С другой стороны, при использовании паттерна Декоратор интерфейс либо остается прежним, либо расширяется. Причём Декоратор поддерживает рекурсивную вложенность, чего не скажешь об Адаптере.
- **Заместитель vs Декоратор**: Используя Заместителя, интерфейс остается неизменным. Используя Декоратор, вы получаете доступ к объекту через расширенный интерфейс.
- **Цепочка обязанностей vs Декоратор**: Оба базируются на рекурсивном выполнении, но обработчики в Цепочке могут прерывать передачу и выполнять независимые действия. Декораторы расширяют определённое действие, не ломая интерфейс и не прерывая выполнение остальных декораторов.
- **Компоновщик vs Декоратор**: Похожие структуры из-за рекурсивной вложенности. Декоратор оборачивает только один объект, узел Компоновщика может иметь много детей. Декоратор добавляет функциональность, Компоновщик «суммирует» результаты детей. Могут сотрудничать.
- **Архитектурное улучшение**: Архитектура, построенная на Компоновщиках и Декораторах, часто может быть улучшена за счёт внедрения Прототипа. Он позволяет клонировать сложные структуры объектов, а не собирать их заново.
- **Стратегия vs Декоратор**: Стратегия меняет поведение объекта «изнутри», Декоратор — «снаружи».
- **Заместитель vs Декоратор (детальное)**: Похожи тем, что оба построены на принципе композиции и делегируют работу другим объектам. Паттерны отличаются тем, что Заместитель сам управляет жизнью сервисного объекта, а обёртывание Декораторов контролируется клиентом.
