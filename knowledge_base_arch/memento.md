# Снимок

## Суть паттерна

**Снимок** — это поведенческий паттерн проектирования, который позволяет сохранять и восстанавливать прошлые состояния объектов, не раскрывая подробностей их реализации.

Паттерн решает классическую задачу реализации функции отмены (undo) без нарушения принципа инкапсуляции. Вместо того чтобы другие объекты лезли в приватные данные сохраняемого объекта, сам объект создаёт снимок своего состояния и передаёт его для хранения.

## Проблема

Предположим разработка текстового редактора с поддержкой отмены операций. Редактор позволяет редактировать текст, менять форматирование, вставлять изображения и выполнять другие действия.

Требуется реализовать функцию отмены. Логичный подход — перед каждой операцией сохранять текущее состояние редактора. При запросе отмены можно восстановить сохранённое состояние.

На первый взгляд решение простое: скопировать значения всех полей редактора перед операцией. Однако этот наивный подход создаёт серьёзные проблемы:

**Проблема с рефакторингом.** Если после реализации этого механизма вы решите изменить структуру класса редактора — добавить или удалить поля — придётся обновлять код всех объектов, которые копировали состояние. Это нарушает принцип открытости/закрытости.

**Проблема с инкапсуляцией.** Чтобы делать копии состояния, нужно сделать все поля редактора доступными для чтения. Но это раскрывает внутреннюю структуру класса остальному коду.

**Проблема с контейнером состояния.** Нужно где-то хранить копии состояния. Логично создать класс-контейнер с множеством полей для хранения каждого аспекта состояния редактора. Однако этот класс также потребует публичных полей для записи и чтения данных, создавая те же проблемы с инкапсуляцией.

Получается дилемма: либо открыть классы для всех, создав проблемы с поддержкой, либо отказаться от функции отмены.

## Решение

Ключ к решению — понимание, что проблемы возникают из-за нарушения инкапсуляции, когда одни объекты пытаются выполнять работу за другими, залезая в их приватные данные.

**Основная идея паттерна:** поручить создание снимка состояния самому объекту, который этим состоянием владеет. Редактор сам создаст копию своих полей, поскольку ему доступны все поля, даже приватные.

Паттерн использует три ключевых роли:

1. **Создатель** (Originator) — объект, состояние которого нужно сохранять. Это редактор.
2. **Снимок** (Memento) — специальный объект с ограниченным интерфейсом, содержащий состояние создателя. Снимок должен быть полностью открыт для своего создателя (позволяя ему читать и восстанавливать состояние), но иметь ограниченный интерфейс для остальных объектов.
3. **Опекун** (Caretaker) — объект, управляющий снимками. Опекун хранит историю снимков, но не имеет доступа к их внутренним данным, работая только с ограниченным интерфейсом.

Эта архитектура позволяет создателям производить снимки и передавать их опекунам для хранения, при этом опекуны не смогут повлиять на внутренности снимка. Когда нужно откатить состояние, опекун передаёт снимок обратно создателю для восстановления.

В примере с редактором опекуном выступает класс истории операций, который хранит список выполненных команд вместе с их снимками. Благодаря ограниченному интерфейсу снимков класс истории может показывать пользователю красивый список с названиями и датами операций, но не может изменить внутренние данные снимков. Когда пользователь решит откатить операцию, история возьмёт нужный снимок и попросит редактор восстановить своё состояние.

## Структура

### Классическая реализация на вложенных классах

Эта реализация использует механизм вложенных классов, доступный в некоторых языках программирования (C++, C#, Java).

1. **Создатель** — может производить снимки своего состояния, а также воспроизводить прошлое состояние из готового снимка. Содержит приватные поля, представляющие его состояние.
2. **Снимок** — простой объект данных, содержащий состояние создателя. Надёжнее всего сделать снимки неизменяемыми, передавая начальное состояние только через конструктор. Снимок реализуется как вложенный класс внутри создателя.
3. **Опекун** — должен знать, когда делать снимок создателя и когда его восстанавливать. Может хранить историю прошлых состояний в виде стека снимков. При необходимости отмены опекун берёт верхний снимок из стека и передаёт его создателю для восстановления.
4. **Ключевое преимущество этого подхода:** снимок, будучи вложенным классом, имеет полный доступ к приватным полям создателя. Одновременно опекун не имеет доступа ни к состоянию, ни к методам снимков и может только хранить ссылки на объекты снимков.

### Реализация с пустым промежуточным интерфейсом

Подходит для языков без механизма вложенных классов (например, PHP).

1. Создатель работает напрямую с конкретным классом снимка, имея полный доступ к его методам и полям.
2. Опекун работает только с ограниченным интерфейсом снимка, который определяет только вспомогательные методы (например, получение даты создания снимка).
3. **Благодаря этому достигается тот же эффект:** создатель имеет полный доступ к снимку для восстановления своего состояния, а опекун не может повлиять на содержимое снимка.

### Снимки с повышенной защитой

Когда нужно полностью исключить возможность доступа к состоянию создателей и снимков, используется более сложная реализация.

1. **Для каждого класса создателей существует свой класс снимков.** Ни создатели, ни снимки не позволяют другим объектам прочесть своё состояние.
2. **Метод восстановления находится в самом снимке**, а не в создателе. Опекун вызывает метод снимка, передав создателя, и снимок самостоятельно восстанавливает состояние своего создателя.
3. **Тесная связь между создателем и его снимком.** Снимки получают состояние через конструктор и знают, как восстановить состояние своего создателя. Эта схема работает, если классы снимков вложены в классы создателей или если создатели предоставляют сеттеры для установки значений полей.
4. **Преимущество этого подхода:** опекун становится полностью независим от создателей, работая с универсальным интерфейсом снимков. Это обеспечивает максимальную защиту инкапсуляции.

## Псевдокод

Пример использует паттерн Снимок совместно с паттерном Команда для реализации функции отмены в текстовом редакторе.

**Сценарий работы:** объекты команд выступают в роли опекунов. Перед выполнением своего действия команда запрашивает у редактора снимок его текущего состояния и сохраняет этот снимок. Снимок содержит полное состояние редактора: текст, позицию курсора, ширину выделения.

Если потребуется отменить операцию, команда вызывает метод восстановления на сохранённом снимке, передав ему объект редактора. Снимок восстанавливает все параметры редактора в то состояние, которое было до выполнения команды.

Снимок не имеет публичных полей, поэтому другие объекты не могут получить доступ к его внутренним данным. Снимки связаны с определённым редактором, который их создал, и они восстанавливают именно его состояние. Это позволяет программе одновременно работать с несколькими редакторами, например открытыми в разных вкладках.

**Структура кода:**

- Класс **Editor** (создатель) имеет приватные поля для текста, позиции курсора и прочего состояния. Содержит метод `createSnapshot()`, который создаёт новый объект снимка, передав ему текущие значения всех полей.
- Класс **Snapshot** (снимок) содержит копию состояния редактора, полученную в конструкторе. Имеет метод `restore()`, который восстанавливает состояние редактора, вызывая его публичные сеттеры.
- Класс **Command** (команда, выступающая опекуном) содержит ссылку на снимок. Перед выполнением действия вызывает `makeBackup()` для создания снимка. При отмене вызывает `undo()`, который восстанавливает состояние из снимка.

## Применимость

**Когда нужно сохранять и восстанавливать прошлые состояния объектов.**

Паттерн Снимок позволяет создавать любое количество снимков объекта и хранить их независимо от объекта, с которого они сделаны. Снимки часто используют не только для реализации функции отмены, но и в сценариях транзакций, когда состояние объекта нужно откатить, если операция не удалась. Например, в базах данных снимки используют для реализации ACID-свойства и возможности отката операций при ошибке.

**Когда прямой доступ к состоянию объекта раскрывает приватные детали его реализации.**

Паттерн предлагает создавать снимок самому исходному объекту, поскольку ему доступны все поля, даже приватные. Это сохраняет инкапсуляцию — другие объекты не могут напрямую обращаться к внутренним данным, а только просят создателя создать снимок. Таким образом, если структура класса изменится, нужно будет обновить только внутреннюю логику создателя и снимка, но не весь остальной код.

## Шаги реализации

1. **Определите класс создателя.** Определите класс объектов, состояние которых нужно сохранять. Это может быть текстовый редактор, объект конфигурации, игровой персонаж или любой другой объект со сложным состоянием.

2. **Создайте класс снимка.** Создайте отдельный класс и опишите в нём все те же поля, которые имеются в оригинальном классе-создателе. Эти поля будут содержать копию состояния создателя.

3. **Сделайте объекты снимков неизменяемыми.** Снимки должны получать начальные значения только один раз через конструктор. После создания они не должны меняться. Это гарантирует, что сохранённое состояние не будет случайно изменено.

4. **Определите доступ к снимкам.** Если ваш язык поддерживает вложенные классы, сделайте класс снимка вложенным в класс создателя. Это обеспечит приватный доступ создателя к снимку и ограничит доступ других объектов. Если язык не поддерживает вложенные классы (например PHP или Python), извлеките из класса снимка пустой интерфейс, который будет доступен остальным объектам программы. Этот интерфейс может включать вспомогательные методы для получения метаданных снимка (дата создания, название операции), но прямой доступ к состоянию создателя должен быть исключён.

5. **Добавьте метод получения снимка в создателя.** Добавьте публичный метод, который создаёт новые объекты снимков и передаёт в их конструктор текущие значения всех своих полей. Сигнатура метода должна возвращать снимки через ограниченный интерфейс, если он определён. Сам же класс должен работать с конкретным классом снимка.

6. **Добавьте метод восстановления в создателя.** Добавьте метод, который восстанавливает состояние создателя из переданного снимка. При определении типов следуйте той же логике, что и в предыдущем пункте.

7. **Определите роль опекуна.** Опекунами могут быть различные объекты: класс истории операций, класс команд, менеджер сохранений и прочие. Опекуны должны знать, когда запрашивать снимки у создателя (например, перед выполнением команды), где их хранить (в стеке, очереди, словаре) и когда восстанавливать состояние (при отмене, при откате, при загрузке).

8. **Рассмотрите тесную связь создателя и снимка.** Можно перенести логику восстановления из создателя в снимок. В этом случае каждый снимок будет привязан к своему создателю и сам восстанавливать его состояние. Эта схема работает, если классы снимков вложены в классы создателей, или если создатели предоставляют публичные сеттеры для всех своих полей, позволяя снимкам менять состояние.

## Преимущества и недостатки

**Преимущества:**

- Паттерн не нарушает инкапсуляцию исходного объекта. Другие объекты не получают прямой доступ к состоянию создателя, а только работают со снимками через ограниченный интерфейс.
- Упрощает структуру исходного объекта. Создатель не должен хранить историю версий своего состояния — эта ответственность переходит к опекунам.

**Недостатки:**

- Требует много памяти, если клиенты слишком часто создают снимки. Каждый снимок содержит полную копию состояния объекта, поэтому частые снимки приводят к значительному потреблению памяти.
- Может повлечь дополнительные издержки памяти, если объекты, хранящие историю снимков, не освобождают ресурсы, занятые устаревшими снимками. Нужно реализовать механизм удаления старых снимков из истории.
- В некоторых языках программирования (PHP, Python, JavaScript) сложно гарантировать, чтобы только исходный объект имел доступ к состоянию снимка. Язык может не предоставлять механизма для полного скрытия приватных полей, поэтому другие объекты потенциально смогут получить доступ к состоянию снимка.

## Отношения с другими паттернами

- **Команда и Снимок совместно.** Паттерны Команда и Снимок часто используют вместе для реализации отмены операций. Объекты команд выступают в роли опекунов и отвечают за выполнение действия над объектом. Перед выполнением команда запрашивает снимок состояния объекта-получателя. Если операция успешна, снимок выбрасывается. Если нужна отмена, команда использует сохранённый снимок для восстановления прошлого состояния.

- **Снимок и Итератор.** Паттерн Снимок можно использовать вместе с паттерном Итератор. Снимок сохраняет текущее состояние обхода структуры данных: текущую позицию, пройденные элементы и прочие параметры итерации. Это позволяет вернуться к определённой точке в обходе структуры в будущем.

- **Снимок и Прототип.** Паттерн Снимок иногда можно заменить паттерном Прототип, если объект, состояние которого требуется сохранять в истории, достаточно прост. Если объект не имеет активных ссылок на внешние ресурсы или эти ресурсы легко восстанавливаются, то можно просто создавать глубокие копии объекта вместо использования специализированных снимков.
