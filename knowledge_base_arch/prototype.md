# Прототип

## Суть паттерна

**Прототип** — это порождающий паттерн проектирования, который позволяет копировать объекты, не вдаваясь в подробности их реализации.

Паттерн решает проблему создания копий объектов без необходимости знать их точные классы и внутреннюю структуру. Вместо того чтобы код клиента знал о деталях копирования, сами объекты берут на себя ответственность за создание своих копий через единый интерфейс.

## Проблема

Представьте ситуацию, когда нужно скопировать существующий объект. Классический подход выглядит просто: создать новый пустой объект того же класса и последовательно скопировать значения всех полей из исходного объекта в новый.

Однако такой способ имеет существенные недостатки:

**Недостаток первый — приватные поля.** Часть состояния объекта может быть скрыто (объявлено как приватное), и внешний код просто не сможет получить доступ к этим данным. Копирование «извне» оказывается невозможным в реальных условиях.

**Недостаток второй — привязка к конкретным классам.** Если копирующий код хочет обойти все поля объекта, он вынужден зависеть от его конкретного класса. Это означает, что невозможно копировать объекты, зная только их интерфейс, без информации о точном типе. Добавляется нежелательная связанность между компонентами.

## Решение

Паттерн Прототип предлагает элегантный выход: позволить самим объектам создавать свои копии. Для этого вводится общий интерфейс, который все копируемые объекты должны реализовать. Обычно этот интерфейс содержит один метод — `clone`.

Каждый класс, поддерживающий клонирование, сам реализует метод `clone`. Реализация создаёт новый объект того же класса и копирует в него все значения полей. Благодаря тому что код находится внутри класса, он имеет доступ к приватным полям (в большинстве языков программирования объекты одного класса могут обращаться к приватным членам друг друга).

Объект, который копируют, называется **прототипом** — отсюда и название паттерна.

Практическое применение: когда программа содержит множество подклассов, которые различаются только начальными значениями своих полей, прототипы становятся отличной альтернативой созданию всех этих подклассов. Вместо этого создают несколько предварительно настроенных экземпляров разных конфигураций, сохраняют их как прототипы и затем копируют из них по мере необходимости. Программа при инициализации подготавливает набор прототипов с нужными конфигурациями, а дальше просто клонирует их.

## Структура

### Базовая реализация

Структура паттерна состоит из трёх основных компонентов:

1. **Интерфейс прототипов** описывает операции клонирования. В большинстве случаев это единственный метод `clone`, который возвращает копию объекта.

2. **Конкретный прототип** реализует операцию клонирования самого себя. Помимо простого копирования значений всех полей, здесь могут скрываться различные сложности, о которых клиент не должен знать. Например: клонирование связанных объектов, распутывание рекурсивных зависимостей и прочие непредвиденные сложности процесса.

3. **Клиент** создаёт копию объекта, обращаясь к нему через общий интерфейс прототипов. Клиент не привязан к конкретным классам и работает только с интерфейсом.

### Реализация с общим хранилищем прототипов

Дополнительный компонент для более сложных сценариев — **хранилище прототипов**, которое облегчает доступ к часто используемым прототипам, храня набор предварительно созданных и настроенных объектов, готовых к копированию. Простейшее хранилище реализуется как хеш-таблица вида «имя-прототипа → прототип». Для удобства поиска прототипы можно маркировать не только условными именами, но и другими критериями.

## Псевдокод

Пример демонстрирует, как паттерн позволяет копировать объекты геометрических фигур, не привязываясь к их конкретным классам.

Все фигуры реализуют интерфейс клонирования и предоставляют метод для воспроизведения самой себя. Базовый класс `Shape` содержит конструктор-копировальщик, который принимает объект того же класса и копирует его поля. Подклассы (например, `Rectangle` и `Circle`) наследуют этот конструктор, добавляя копирование своих собственных полей, и реализуют метод `clone`, создавая новый экземпляр собственного класса.

Ключевой момент: метод `clone` состоит всего из одной строки — вызова `new` с конструктором прототипа. Благодаря этому операция клонирования атомарна. Клиентский код может копировать объекты «вслепую» через полиморфизм, не зная их точные типы.

## Применимость

**Когда код не должен зависеть от классов копируемых объектов.**

Такое часто бывает, если код работает с объектами, поданными извне через какой-то общий интерфейс. Вы не можете привязаться к их классам, даже если бы хотели, поскольку конкретные типы неизвестны на момент написания кода.

Паттерн Прототип предоставляет клиенту единый интерфейс для работы со всеми прототипами. Клиент зависит только от интерфейса клонирования, а не от всех классов копируемых объектов. Это обеспечивает слабую связанность.

**Когда у вас есть множество подклассов, отличающихся только начальными значениями полей.**

Иногда разработчики создают целую иерархию классов только для того, чтобы получать объекты с определёнными предустановленными конфигурациями.

Паттерн Прототип предлагает альтернативу: вместо создания множества подклассов используется набор предварительно сконфигурированных прототипов. Вы копируете существующие объекты с нужным внутренним состоянием вместо порождения объектов из новых подклассов. Это позволяет избежать взрывного увеличения количества классов и упрощает архитектуру программы.

## Шаги реализации

1. **Создание интерфейса прототипов.** Добавьте интерфейс с единственным методом `clone`. Если у вас уже существует иерархия продуктов, метод клонирования можно объявить непосредственно в каждом из её классов, не создавая отдельный интерфейс.

2. **Добавление конструктора-копировальщика.** Внесите в классы будущих прототипов альтернативный конструктор, который принимает в качестве аргумента объект того же класса. Этот конструктор должен скопировать значения всех полей из переданного объекта в новый объект, а затем вызвать родительский конструктор, чтобы тот позаботился о полях, объявленных в суперклассе. Если язык программирования не поддерживает перегрузку методов, копирование можно проводить в отдельном методе, созданном для этих целей — конструктор удобнее, так как позволяет клонировать объект за один вызов.

3. **Реализация метода клонирования.** Метод `clone` обычно состоит всего из одной строки: вызова оператора `new` с конструктором прототипа. Все классы, поддерживающие клонирование, должны явно определить метод `clone`, чтобы использовать собственный класс с оператором `new`. В противном случае результатом клонирования станет объект родительского класса.

4. **(Опционально) Создание хранилища прототипов.** Создайте центральное хранилище прототипов для удобного доступа к различным вариантам объектов, возможно разных классов, но с разными конфигурациями. Хранилище можно разместить либо в новом фабричном классе, либо в фабричном методе базового класса прототипов. Фабричный метод должен на основе входящих аргументов искать в хранилище подходящий экземпляр, вызывать его метод клонирования и возвращать полученный объект.

5. **Замена прямых вызовов конструкторов.** Избавьтесь от прямых вызовов конструкторов объектов в коде, заменив их вызовами фабричного метода хранилища прототипов.

## Преимущества и недостатки

**Преимущества:**

- Позволяет клонировать объекты, не привязываясь к их конкретным классам.
- Сокращает повторяющийся код инициализации объектов.
- Ускоряет создание объектов, особенно когда конструкторы сложные.
- Служит альтернативой созданию подклассов для конструирования сложных объектов.

**Недостатки:**

- Сложно клонировать составные объекты, имеющие ссылки на другие объекты, особенно если в этих ссылках присутствуют циклические зависимости.

## Отношения с другими паттернами

- Многие архитектуры начинаются с применения Фабричного метода (более простого и расширяемого через подклассы) и эволюционируют в сторону Абстрактной фабрики, Прототипа или Строителя (более гибких, но и более сложных). Классы Абстрактной фабрики часто реализуются с помощью Фабричного метода, хотя могут быть построены и на основе Прототипа.
- Если Команду нужно копировать перед вставкой в историю выполненных команд, может помочь Прототип.
- Архитектура, построенная на Компоновщиках и Декораторах, часто может быть улучшена за счёт внедрения Прототипа. Он позволяет клонировать сложные структуры объектов, а не собирать их заново из отдельных компонентов.
- Прототип не опирается на наследование, но требует сложной операции инициализации. Фабричный метод, наоборот, построен на наследовании, но не требует сложной инициализации исходных прототипов.
- Снимок иногда можно заменить Прототипом, если объект, состояние которого требуется сохранять в истории, довольно простой, не имеет активных ссылок на внешние ресурсы либо их можно легко восстановить.
- Абстрактная фабрика, Строитель и Прототип могут быть реализованы при помощи Одиночки (как глобального реестра предварительно созданных объектов).
