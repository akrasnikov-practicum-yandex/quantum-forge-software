# Фасад

## Суть паттерна

Фасад — это структурный паттерн проектирования, который предоставляет простой интерфейс к сложной системе классов, библиотеке или фреймворку.

## Проблема

Вашему коду часто требуется работать с множеством объектов сложной библиотеки или фреймворка. Необходимо самостоятельно инициализировать эти объекты, отслеживать правильный порядок зависимостей и управлять всеми деталями взаимодействия.

В результате бизнес-логика ваших классов становится тесно переплетена с деталями реализации сторонних классов, что делает код сложным для понимания и поддержки.

## Решение

Фасад предоставляет простой интерфейс для работы со сложной подсистемой, содержащей множество классов. Фасад может иметь урезанный интерфейс без полной функциональности, доступной при прямом использовании сложной подсистемы. Однако он предоставляет именно те функции, которые нужны клиенту, скрывая все остальное.

Фасад особенно полезен при работе со сложной библиотекой, когда требуется только часть её возможностей. Например, программа для загрузки видео в социальные сети может использовать профессиональную библиотеку сжатия видео, но клиентскому коду нужен только простой метод `encode(filename, format)`. Создав класс с таким методом, вы реализуете фасад.

## Структура

1. **Фасад** — предоставляет быстрый доступ к определённой функциональности подсистемы. Он «знает», каким классам нужно переадресовать запрос, и какие данные для этого требуются.

2. **Дополнительный фасад** — может быть введён, чтобы избежать «захламления» единого фасада разнородной функциональностью. Его могут использовать как клиент, так и другие фасады.

3. **Сложная подсистема** — состоит из множества разнообразных классов. Чтобы заставить их выполнять задачу, необходимо знать подробности устройства подсистемы, порядок инициализации объектов и другие детали. Классы подсистемы не знают о существовании фасада и работают друг с другом напрямую.

4. **Клиент** — использует фасад вместо прямой работы с объектами сложной подсистемы.

## Псевдокод

В этом примере фасад упрощает работу со сложным фреймворком видеоконвертации. Вместо непосредственной работы с дюжиной классов, фасад предоставляет единственный метод для конвертации видео, который сам заботится о правильной конфигурации нужных объектов фреймворка и получении требуемого результата.

Приложение не зависит от сложного фреймворка конвертации видео. При необходимости смены фреймворка нужно переписать только класс фасада.

## Применимость

**Когда нужно представить простой или урезанный интерфейс к сложной подсистеме.**

По мере развития программы подсистемы часто усложняются. Применение большинства паттернов приводит к появлению меньших классов, но в большем количестве. Такую подсистему проще повторно использовать, настраивая её под конкретные нужды, но применять подсистему без настройки становится сложнее. Фасад предлагает определённый вид системы по умолчанию, устраивающий большинство клиентов.

**Когда требуется разложить подсистему на отдельные слои.**

Используйте фасады для определения точек входа на каждый уровень подсистемы. Если подсистемы зависят друг от друга, зависимость можно упростить, разрешив подсистемам обмениваться информацией только через фасады.

Например, в сложной системе видеоконвертации можно разбить её на слои работы с аудио и видео. Для каждой части можно создать фасад и заставить классы аудио и видео обработки общаться друг с другом через эти фасады, а не напрямую.

## Шаги реализации

1. Определите, можно ли создать более простой интерфейс, чем предоставляемый сложной подсистемой. Вы на правильном пути, если этот интерфейс избавит клиента от необходимости знать подробности подсистемы.

2. Создайте класс фасада, реализующий этот интерфейс. Он должен переадресовывать вызовы клиента нужным объектам подсистемы. Фасад должен позаботиться о правильной инициализации объектов подсистемы.

3. Максимум пользы получите, если клиент будет работать только с фасадом. В этом случае изменения в подсистеме будут затрагивать только код фасада, а клиентский код останется работоспособным.

4. Если ответственность фасада начинает размываться, подумайте о введении дополнительных фасадов.

## Преимущества и недостатки

**Преимущества:**
- Изолирует клиентов от компонентов сложной подсистемы.

**Недостатки:**
- Фасад рискует стать «божественным объектом», привязанным ко всем классам программы.

## Отношения с другими паттернами

- **Фасад vs Адаптер**: Фасад задаёт новый интерфейс, тогда как Адаптер повторно использует старый. Адаптер оборачивает только один класс, а Фасад оборачивает целую подсистему. Кроме того, Адаптер позволяет двум существующим интерфейсам работать сообща, вместо того чтобы задать полностью новый.
- **Фасад vs Абстрактная фабрика**: Абстрактная фабрика может использоваться вместо Фасада для скрытия платформо-зависимых классов.
- **Фасад vs Легковес**: Легковес показывает, как создавать много мелких объектов, а Фасад показывает, как создать один объект, отображающий целую подсистему.
- **Фасад vs Посредник**: Оба паттерна пытаются организовать работу множества существующих классов, но по-разному. Фасад создаёт упрощённый интерфейс к подсистеме без добавления функциональности; сама подсистема не знает о существовании Фасада, и классы общаются напрямую. Посредник централизует общение между компонентами; компоненты знают только о Посреднике и не имеют прямого доступа друг к другу.
- **Фасад и Одиночка**: Фасад можно сделать Одиночкой, так как обычно нужен только один объект-фасад.
- **Фасад vs Заместитель**: Оба замещают сложную подсистему и могут инициализировать её. Но Заместитель имеет тот же интерфейс, что его служебный объект, благодаря чему их можно взаимозаменять, тогда как Фасад — нет.
