## Введение: контекст и ограничения

QuantumForge Software — финско-эстонская продуктовая компания (SaaS-платформа «Digital Twin»).
База знаний насчитывает ≈18 000 Markdown-файлов, ≈3 000 страниц Confluence, ≈250 PDF,
прирост ~400 страниц в месяц. Пользователи — разработчики, служба поддержки, менеджеры,
новые сотрудники.

**Ключевое ограничение — конфиденциальность данных.**  
Документация содержит архитектурные решения, параметры SCADA-интеграций, контрактные
спецификации и материалы SOC 2-аудита. Отправка этих данных в сторонние облачные API
(OpenAI, YandexGPT) создаёт риски утечки и нарушение требований SOC 2.
Это «красная нить» всех рекомендаций: **данные должны оставаться в инфраструктуре
компании или пересекать периметр только в зашифрованном/анонимизированном виде.**

## 1. Сравнение LLM-моделей

### Локальные (Hugging Face) vs облачные (OpenAI GPT-4 / YandexGPT)

| Критерий | Облачные (OpenAI GPT-4, YandexGPT) | Локальные (Hugging Face: Mistral 7B, Llama 3) |
|---|---|---|
| **Качество ответов** | Высокое — лидеры бенчмарков, умеют рассуждать и суммаризировать | Варьируется; топовые 7B–13B-модели сопоставимы на узкоспециализированных задачах |
| **Скорость работы** | Зависит от сети и rate limits API (100–500 мс на запрос) | Зависит от железа: GPU обязателен для приемлемого inference (< 2 с при 7B на A10G) |
| **TCO (стоимость владения)** | Pay-per-token: GPT-4 ≈ $0.01–0.03 / 1K токенов; при 100+ запросах/день быстро накапливается | Только инфраструктура (GPU-сервер / облачный инстанс); высокий upfront, низкий marginal cost |
| **Развёртывание** | Минимальное: API-ключ + `pip install openai` | Требует GPU, загрузки весов (7B ≈ 14 GB), настройки `transformers` или `llama.cpp` |
| **Конфиденциальность** | ❌ Данные передаются в API провайдера | ✅ Данные остаются внутри периметра |
| **Соответствие SOC 2** | ⚠️ Требует DPA с провайдером; риски при передаче чувствительных чанков | ✅ Полный контроль |

**Вывод по LLM:** для прототипа спринта (небольшой объём, учебный кейс) OpenAI-подход
приемлем при условии анонимизации запросов. Для production QuantumForge предпочтителен
**гибридный вариант** (облачная LLM для генерации, локальные эмбеддинги для индексации)
или полностью локальная модель при наличии GPU.

## 2. Сравнение моделей эмбеддингов

### Локальные (Sentence-Transformers) vs облачные (OpenAI Embeddings)

| Критерий | Локальные (Sentence-Transformers) | Облачные (OpenAI Embeddings) |
|---|---|---|
| **Примеры моделей** | `all-MiniLM-L6-v2` (384-dim, ~22 MB), `bge-base-en` (768-dim), `paraphrase-multilingual-MiniLM-L12-v2` (384-dim, мультиязычная с русским) | `text-embedding-ada-002`, `text-embedding-3-small/large` |
| **Скорость индексации** | Быстро на GPU; `all-MiniLM-L6-v2` ≈ 5–10 мс на предложение на CPU | Зависит от сетевого лага и rate limits; батч-обработка ускоряет |
| **Качество поиска** | Хорошее; `bge-base-en` — один из лидеров публичных бенчмарков для английского | Высокое; `text-embedding-3-large` (3072-dim) превосходит большинство open-source |
| **TCO** | Только инфраструктура — нет pay-per-token; 18 000 документов индексируются один раз | Pay-per-token: `ada-002` ≈ $0.0001 / 1K токенов; при большом объёме и переиндексации накапливается |
| **Конфиденциальность** | ✅ Данные не покидают инфраструктуру | ❌ Текст документов передаётся в API |
| **Железо** | CPU достаточен для `all-MiniLM-L6-v2`; GPU ускоряет большие модели | Не нужен |

### Рекомендуемая embedding-модель для QuantumForge

`all-MiniLM-L6-v2` — оптимальный выбор для прототипа:
- Компактная (≈22 MB), быстрая (CPU-inference), хорошее качество для английского.
- Данные не покидают инфраструктуру — соответствует требованиям SOC 2.

Для production с русскоязычными документами (Confluence-пространства, PDF-регламенты
на русском): `paraphrase-multilingual-MiniLM-L12-v2`.  
Для максимального качества поиска (английский): `bge-base-en` или `e5-base`.

## 3. Сравнение векторных баз данных: FAISS vs ChromaDB (+ Qdrant)

| Критерий | FAISS | ChromaDB | Qdrant |
|---|---|---|---|
| **Тип** | Библиотека (in-process) | Embedded / сервер | Отдельный сервис |
| **Скорость поиска** | Очень высокая (C++-ядро, оптимизирован для CPU/GPU) | Средняя (Python, ограничен RAM) | Высокая (Rust, один из лидеров бенчмарков) |
| **Скорость индексации** | Высокая; `IndexFlatIP` — точный поиск, `IndexHNSWFlat` — ANN с O(log N) | Средняя | Высокая (HNSW-индекс встроен) |
| **Сложность внедрения** | Минимальная: `pip install faiss-cpu` | Минимальная: `pip install chromadb` | Средняя: `docker run qdrant/qdrant` + API |
| **Персистентность** | Ручное: `faiss.write_index(index, "faiss.index")` | Встроенная (автоматически на диск) | Встроенная + snapshots |
| **Фильтрация по метаданным** | ❌ Нет нативной; нужны битсет-маски или постфильтрация | ✅ Нативная: `where={"source": "onboarding.md"}` | ✅ Мощная: числовые диапазоны, geo, сложные условия |
| **TCO** | Только инфраструктура | Бесплатно (open-source) | Бесплатно (open-source) + managed cloud |
| **GPU-поддержка** | Да (`faiss-gpu`) | Нет | Нет |
| **Рекомендуется для** | Прототипы, максимальная скорость, полный контроль | Локальные PoC, удобный Python API | Production с метафильтрацией и масштабом |

### Алгоритм HNSW в контексте QuantumForge

FAISS поддерживает `IndexHNSWFlat` — алгоритм с многослойным навигируемым графом,
обеспечивающий O(log N) поиск. При 18 000+ документов и среднем чанке ≈200 слов
индекс содержит ~100 000–200 000 векторов: HNSW справляется без квантизации.
Для прототипа достаточно `IndexFlatIP` (точный поиск, никаких потерь качества).

## 4. Конфигурация сервера (CPU / RAM / GPU)

| Компонент стека | CPU | GPU | RAM |
|---|---|---|---|
| `all-MiniLM-L6-v2` inference | ✅ достаточно (5–10 мс/предложение) | Ускоряет батч-индексацию | 4 GB достаточно |
| `faiss-cpu` поиск | ✅ достаточно | Не нужен для < 1 M векторов | Индекс 100K × 384-dim ≈ 150 MB |
| OpenAI GPT-4 (генерация через API) | ✅ CPU/сеть | Не нужен | — |
| Локальная LLM 7B (Mistral / Llama) | ❌ слишком медленно | ✅ обязателен (VRAM ≥ 16 GB) | 16–32 GB system RAM |
| LangChain-оркестрация | ✅ CPU | — | 2–4 GB |

### Рекомендуемые конфигурации серверов под варианты стека

**Прототип (вариант D, см. ниже):**
- CPU: 4 ядра (любой modern x86-64)
- RAM: 8 GB
- Диск: 20 GB SSD
- GPU: не нужен
- Облако: `t3.large` AWS (~$0.08/ч) или аналог

**Production без локальной LLM (вариант B):**
- CPU: 8 ядер
- RAM: 16 GB
- Диск: 100 GB SSD (для индексов и персистентности Qdrant)
- GPU: не нужен (эмбеддинги быстро на CPU)

**Production с локальной LLM (вариант C):**
- CPU: 8–16 ядер
- RAM: 32 GB
- Диск: 200 GB SSD
- GPU: NVIDIA A10G / A100 (VRAM ≥ 16 GB) — обязателен для inference LLM

## 5. Итоговые рекомендации: 4 варианта инфраструктуры

### Вариант A — Полностью облачный

| Компонент | Технология |
|---|---|
| LLM | OpenAI GPT-4 / GPT-4o |
| Embedding | OpenAI `text-embedding-3-small` |
| Векторная БД | Pinecone (SaaS) |
| Инфраструктура | Только CPU-сервер |

**Плюсы:** минимальный порог входа, нет сопровождения моделей, высокое качество.  
**Минусы:** данные уходят в API OpenAI и Pinecone — **прямой конфликт с требованиями
SOC 2 QuantumForge**. Стоимость при 100+ запросах/день быстро растёт.  
**Оценка: ❌ неприемлемо** без явной DPA и разрешения GRC-команды.

---

### Вариант B — Гибридный (облачная LLM + локальные эмбеддинги)

| Компонент | Технология |
|---|---|
| LLM | OpenAI GPT-4o (только генерация, финальный ответ) |
| Embedding | `all-MiniLM-L6-v2` (Sentence-Transformers) |
| Векторная БД | ChromaDB или FAISS |
| Инфраструктура | CPU-сервер + Docker |

**Плюсы:** корпоративные документы индексируются локально, в API уходит только
анонимизированный пользовательский запрос + найденные чанки. Хорошее качество ответов.  
**Минусы:** передача чанков в GPT-API всё равно несёт риск утечки;
нужна дополнительная анонимизация или DPA с OpenAI.  
**Оценка: ⚠️ условно приемлемо** — переходный вариант до полного on-prem.

---

### Вариант C — Полностью локальный / on-prem

| Компонент | Технология |
|---|---|
| LLM | Mistral 7B / Llama 3 8B (Hugging Face) |
| Embedding | `all-MiniLM-L6-v2` или `bge-base-en` |
| Векторная БД | Qdrant (Docker, on-prem) |
| Инфраструктура | GPU-сервер (A10G 24 GB VRAM) |

**Плюсы:** максимальный контроль, 100% соответствие SOC 2, нет зависимости от внешних API,
постоянная стоимость (только инфраструктура).  
**Минусы:** высокий upfront capEx на GPU; качество open-source LLM ниже GPT-4
(особенно для сложных рассуждений); нужна DevOps-инфраструктура для обновления моделей.  
**Оценка: ✅ оптимально для production** при наличии GPU и DevOps-ресурсов.

---

### Вариант D — Прототип спринта (рекомендуемый для проектной работы) ⭐

| Компонент | Технология |
|---|---|
| LLM | OpenAI GPT-3.5-turbo / GPT-4o-mini (через API) |
| Embedding | `all-MiniLM-L6-v2` (Sentence-Transformers, локально) |
| Векторная БД | **FAISS** (`faiss-cpu`, в Docker-контейнере) |
| Оркестрация | LangChain |
| Инфраструктура | CPU-сервер / ноутбук + Docker Compose |

**Плюсы:**
- Минимальный вход: `pip install faiss-cpu langchain sentence-transformers`
- Данные корпуса индексируются локально — эмбеддинги не уходят в API
- Максимальная скорость поиска (C++-ядро FAISS, in-process)
- Полный контроль над алгоритмом ANN (FlatIP → HNSW → IVF при росте)
- Работает на MacBook/CPU-ноутбуке без GPU
- Совпадает с рекомендованным стеком методички (Python 3.11 + LangChain + FAISS + Docker)

**Минусы:**
- FAISS не имеет нативной фильтрации по метаданным (нужна постфильтрация по списку id)
- Персистентность — ручная (`faiss.write_index` / `faiss.read_index`)
- При масштабе > 5–10 M векторов потребуется миграция

**Оценка: ✅ рекомендуется для прототипа.** Путь к production — миграция на Qdrant,
где тот же Python-код через LangChain изменяется минимально.

## Итоговый выбор и аргументация

| # | Критерий | Выбор |
|---|---|---|
| **Векторная БД** | FAISS (прототип) → Qdrant (production) | FAISS: нулевая инфраструктура, max скорость, данные локальны; Qdrant — следующий шаг для метафильтрации |
| **Embedding-модель** | `all-MiniLM-L6-v2` | Конфиденциальность + нет платы за токены + CPU-inference достаточен |
| **LLM** | OpenAI GPT-4o-mini (прототип) / Mistral 7B (production) | Быстрый старт vs SOC 2-контроль |
| **Сервер** | 4 CPU / 8 GB RAM / Docker (прототип); GPU A10G для production LLM | Экономия capEx на прототипе |

**Рекомендация для QuantumForge:**  
Начать с **Варианта D** (FAISS + Sentence-Transformers + GPT-4o-mini), чтобы быстро
показать ценность бота. Параллельно запустить пилот **Варианта C** (полный on-prem)
на GPU-инстансе для команды с наивысшими требованиями к конфиденциальности (GRC, Legal).
После успешного пилота — мигрировать на Qdrant + локальную LLM как единый production-стек.

**Итоговый ответ по главному вопросу задания — «Какую векторную БД использовать?»**

> **FAISS** — для прототипа и быстрого старта. Причины: минимальный порог входа
> (`pip install faiss-cpu`), максимальная скорость in-process поиска, данные не покидают
> инфраструктуру, прямая интеграция с LangChain (`FAISS.from_documents(...)`), файловая
> персистентность (`faiss.index`). При росте масштаба и потребности в метафильтрации —
> **Qdrant** как долгосрочная production-замена без переписывания логики.
